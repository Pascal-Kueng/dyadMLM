# Cross-sectional Gaussian partner-dependence checks

Does your model reproduce how much partners' responses vary and how strongly
they are related? These experimental functions compare the observed pattern
with complete datasets generated by your fitted model.

Start with `simulate_dyad_responses()` to create a reusable collection of
simulated responses. Then use `check_partner_dependence()` to compare partner
summaries, print the results, or plot them. You can reuse the same simulations
for different views of the data.

## Quick start

This example uses the first 40 female-male dyads in the shipped `dyads_cross`
data. The model allows different average responses for the two roles but
assumes equal remaining variation and a nonnegative partner correlation.

```r
library(dyadMLM)

example_data <- dyads_cross[dyads_cross$coupleID <= 40, ]
model <- glmmTMB::glmmTMB(
  closeness ~ gender + (1 | coupleID),
  data = example_data
)

simulations <- simulate_dyad_responses(model, nsim = 1000, seed = 123)
partner_check <- check_partner_dependence(
  simulations,
  dyad = coupleID,
  role = gender,
  plot = FALSE
)

print(partner_check)
plot(partner_check, parameterization = "member", ask = FALSE)
```

Here, `coupleID` and `gender` select columns used in fitting the model. The
check returns a reusable result: printing or plotting it does not simulate
again. For a comparison with more flexible and more restricted models, see the
[short worked review](partner-dependence-review.Rmd) or
[extended example](partner-dependence-vignette-draft.Rmd).

## Reading the results

Each plot shows the range of a summary across simulated datasets, with the
observed value marked. The printed result gives the observed value, simulated
median, middle 95% of simulated values, and the observed position among them.
A position near 0 or 1 means the observation is near an edge of what the model
generated: a reason to investigate that aspect of the model.

These positions are descriptive, **not p-values**. The middle 95% interval is
not a calibrated acceptance region. A close match does not establish good fit:
a model that estimated the same pattern freely from the data will usually
reproduce it. The check is most informative when examining a restriction, such
as equal variation for both roles or no remaining partner correlation.

It does not test whether the partner correlation is zero, identify which
covariance component is wrong, or validate model-based standard errors.

## Choosing what to check

- **Meaningful roles:** supply `role`. The member view shows each role's SD and
  the partner correlation. Use `role = NULL` only if the members are
  substantively interchangeable; that view estimates a common member SD and
  partner correlation without depending on who is listed first.
- **Remaining variation:** the default, `response = "model-centred"`, removes
  the fitted mean pattern from observed and simulated responses in the same
  way. Use `response = "raw"` to retain that pattern. Both choices can reuse
  the same `simulations` object.
- **Alternative view:** `plot(partner_check, parameterization = "mean_difference")`
  shows variation in dyad averages and half-differences, plus their correlation
  when roles are supplied. This expresses the same paired covariance
  information as the member view; it is not an independent test.

## Supported models and data

The current workflow supports Gaussian identity-link `glmmTMB` models with one
numeric response per fitted row, unit case weights, and no zero-inflation
component. The checker requires cross-sectional data: at most two fitted rows
per dyad and at least three complete dyads. With roles, complete dyads must each
contain one member of each of exactly two roles. Missing identifiers and
incomplete dyads are omitted and counted.

Support for other model families, `brms`, repeated dyad observations, and
response-distribution diagnostics is future work.

## Technical details

### What is simulated?

The fitted parameters and fitted-row design stay fixed. Each replicate redraws
all modeled random effects, including any dispersion random effects, and
Gaussian observation errors. With dyads as the only grouping factor, these are
hypothetical new dyads under the same design.

The observed statistic `T(y)` is compared with the same statistic `T(y_rep)` in
each replicate. This is a full-data plug-in predictive reference: no model is
refitted, no observations are held out, and parameter uncertainty is excluded.
The constructor saves and restores the model's simulation settings after both
success and errors. With `seed` supplied, it also restores the caller's random-
number state.

For Gaussian identity-link models, the stored `response_center` is the
prediction with random effects set to zero, equal to the mean over newly drawn
zero-mean random effects. The centred check subtracts this same vector from
every dataset. Newly generated random-effect and observation-level variation
remain; these values are not conditional or PIT residuals.

### Object shapes

Let `n` be the number of rows actually used in fitting and `k` the number of
summaries (six with roles, four without).

| Object component | Shape and meaning |
| --- | --- |
| `simulations$model_frame` | `n` rows: the variables used in fitting, in fitted-row order |
| `simulations$observed_response` | Numeric vector of length `n`: one observed response per fitted row |
| `simulations$response_center` | Numeric vector of length `n`: one fitted mean per fitted row |
| `simulations$simulated_responses` | Numeric matrix, `nsim` rows by `n` columns: one complete simulated dataset per row |
| `partner_check$statistics_table` | `k` rows by eight columns: three labels/identifiers and five numbers per summary |
| `partner_check$replicated_statistics` | Numeric matrix, `nsim` rows by `k` columns: every simulated summary |

The check also stores role labels, complete-pair and omission counts, the
selected response representation, and simulation metadata. The five numeric
table columns are `observed_value`, `replicated_median`, `replicated_lower`,
`replicated_upper`, and `observed_quantile`. The last equals
`(1 + sum(simulated <= observed)) / (nsim + 1)`.

All observed and replicated statistics must be finite. The current Gaussian
check stops if even one dataset has an undefined summary, for example a
correlation with insufficient variation; it does not silently drop that draw.

### Pairing and interchangeable members

One pair map is reused for observed and simulated responses. It has one row per
complete dyad and two columns containing the partners' fitted-row positions.
Rows with missing dyad identifiers are omitted and counted; missing roles are
counted separately among the remaining rows. Dyads with fewer than two usable
rows are incomplete. More than two fitted rows for a known dyad is an error.
Role labels determine pair direction when supplied.

For interchangeable members, the calculation combines the dyad-mean variance
with the half-difference mean square about zero to recover the common member
variance and covariance. Using zero rather than the sample mean keeps the
summaries unchanged by arbitrary member swaps. The plot shows the square root,
labelled “Half-difference RMS (about zero)”.

### Selecting identifiers in code

`dyad` and `role` use column-first tidy evaluation. An unquoted name selects a
fitted column before an equally named external object. Quoted column names also
work. Use `.data$column` or `.data[[column_name]]` for explicit column selection,
and `.env$vector` for an external vector.

External vectors must already match the fitted rows in length and order,
including any omissions made during fitting. The original source-data order
alone is not sufficient. Forward wrapper arguments with embracing:

```r
check_partners <- function(simulations, dyad, role = NULL) {
  check_partner_dependence(
    simulations, dyad = {{ dyad }}, role = {{ role }}, plot = FALSE
  )
}
```

## Development and validation

Source code, generated help, and tests are authoritative if they differ from
this development note. The implementation and tests are in
`R/simulate_dyad_responses.R`, `R/predictive_checks_dependence.R`, and the
corresponding `tests/testthat/test-*.R` files; their help is generated in `man/`.

Package tests cover model restrictions, object dimensions and fitted-row
alignment, seeded reproducibility and restored simulation settings, tidy
evaluation and wrappers, pairing and omissions, manual summary calculations,
covariance identities, reference summaries, printing, and plotting.

Development reports serve different purposes:

- [Worked review](partner-dependence-review.Rmd): shipped data, intended and
  constrained models, distinguishable and interchangeable dyads.
- [Extended example](partner-dependence-vignette-draft.Rmd): a fuller model
  sequence using the same public workflow.
- [Reference validation](partner-dependence-reference-validation.Rmd):
  independent reconstruction of the Woody–Sadler exchangeable calculation and
  supplementary Dingy software cross-check.
- [Repeated simulation study](partner-dependence-outer-simulation-study.Rmd):
  data generated from known Gaussian populations, refitted models, and behavior
  of the complete check. This development report is not run in CI.

Before review or merge, regenerate Rd files, run focused and full tests, render
the development documents, run the package check, and verify CI on the exact
PR head.

### Follow-up plan

Keep `simple-generalized-checks`, `gaussian-ild-prototype`, and
`diagnostic-prototypes` as references. Build fresh branches from the accepted
foundation: non-Gaussian cross-sectional checks first, then Gaussian ILD. Reuse
the response collection, paired summaries, reference summarizer, and plotting
helpers. Keep the ILD path explicitly restricted to Gaussian identity-link
models until generalized ILD has its own validation.

Before extending support, reconcile undefined-statistic behavior in one shared
summarizer with explicit policies and counts of defined simulations. The
current Gaussian check retains its finite-statistic requirement. Distribution
checks and correlation-aware QQ/PIT displays are a separate follow-up in the
[roadmap](../roadmap.md).
